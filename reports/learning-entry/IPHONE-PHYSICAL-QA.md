# iPhone 実機 QA・QM

2026-09-19。学習機能の公開候補 `c0fa8fad8e6dfe455352cc4a8da7dc78873b8956` を、USB接続した物理iPhoneのSafariで確認した。下記6グループはすべて成功。今回、アプリ本体の追加修正は不要だった。

## 対象と方法

- 端末識別モデル `iPhone17,3`、端末から取得したOS `26.5.2`。Safariの表示バージョンも26.5.2。User-Agentの `iPhone OS 18_7` はOS判定に用いない。
- 縦向きの表示領域393 × 695 CSS px、devicePixelRatio 3。画像は実機WebKitから取得したページ画像で、OS全体のスクリーンショットではない。
- Xcodeは起動せず、`pymobiledevice3 11.15.5` のUSB Web Inspector接続を使用。接続先はユーザーが開いた検査用のExample Domainタブに限定した。
- Mac上の公開用ビルド（localhost:4178）のHTML・JS・CSSを、検査対象タブのHTTP応答として渡した。URLは `https://example.com/learn` だが、Example DomainへMGXを公開・アップロードしたわけではない。本番の通信・証明書の検証とは分ける。
- 実行スクリプトは `iphone-physical-qa.mjs`。単一ページのデバッグ接続でDOMのクリック・フォーム入力を実行し、実機のReact、WebKit、localStorageの結果を確認する。画面サイズやUser-Agentのエミュレーションは使用しない。

## 接続とテスト手順の切り分け

- 接続初期はSafariのページが応答せず、iPhoneで検査用ページを前面表示して解消した。設定オン・タブ一覧の取得だけを実機テスト成功とは数えていない。
- 存在しない検査用ホストへの遷移では検査用の通信設定が引き継がれず、Safariの「サーバが見つかりません」になった。同じオリジン内の検査用応答へ切り替えた。アプリ本体の障害として扱わない。
- この接続でPlaywrightの初期化スクリプトと再読み込み後の要素待ちが安定しなかったため、最終実行は単一ページのWeb Inspector接続で行った。クイズは乱数固定せず、画面に実際に出題された問題に合わせて回答した。
- 再読み込みの完了応答だけでは旧画面が残っていたため、新しいdocumentとReact画面の出現を待つようにした。読み込み中も状態を問い合わせる方式で、検査用接続のイベント待ちを解消した。
- 途中失敗を成功数に含めない。最終の6グループ連続実行は2026-09-19 21:39 JSTに成功した。アプリコードに検査用の回避処理は加えていない。
